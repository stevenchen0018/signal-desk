# Signal Desk

用 Go、Gin 和 SQLite 实现的监控与通知工具。浏览器后台管理 IMAP 收件、正文提取、ModelVerse 上下线监控和通知渠道。网页资源随可执行文件一起打包。

## 启动

需要 Go 1.25 或以上版本。SQLite 驱动为纯 Go 实现。

```bash
go build -o signal-desk ./cmd/signal-desk
printf '输入管理员初始密码（至少 12 个字符）\n'
IFS= read -rs SIGNALDESK_ADMIN_PASSWORD
export SIGNALDESK_ADMIN_PASSWORD
./signal-desk
```

访问 [本地管理后台](http://127.0.0.1:8787)，用户名默认为 `admin`。初次启动可通过 `SIGNALDESK_ADMIN_USER` 设置用户名。管理员创建后，密码通过后台的「账号设置」更新，修改后所有登录会话失效。后续启动可直接执行 `./signal-desk`。

| 启动参数 | 默认值 | 用途 |
| --- | --- | --- |
| `-listen` | `127.0.0.1:8787` | 后台监听地址 |
| `-data` | `./data` | SQLite 与配置密钥的目录 |
| `-secure-cookie` | 关闭 | 通过 HTTPS 反向代理访问时启用，代理需保留原始 Host |

## 本地打包与上传

在项目根目录运行 `./scripts/package.sh`。默认交叉编译 Linux amd64，产物和 SHA-256 校验文件会放在 `dist/`。ARM 服务器使用 `--arch arm64`。压缩包只包含可执行文件。

```bash
./scripts/package.sh --arch amd64 --upload deploy@example.com:/opt/signal-desk/releases/ --port 22
```

上传目录须已存在。上传后在服务器的产物目录执行 `sha256sum -c signal-desk-linux-amd64.tar.gz.sha256` 和 `tar -xzf signal-desk-linux-amd64.tar.gz`。运行时通过 `-data` 指向服务器上的数据目录。

## 项目结构

```text
signal-desk/
├── cmd/signal-desk/    # 命令入口，组装后台、SQLite 和任务进程
├── internal/
│   ├── admin/          # Gin 路由、中间件、页面和表单
│   │   ├── templates/  # Go HTML 模板
│   │   └── static/     # CSS 和 JavaScript，随程序嵌入
│   ├── config/         # 配置类型、校验、邮件提取规则及通知模板
│   ├── store/          # SQLite 表结构、查询、事务和配置加密
│   └── worker/         # 定时轮询、IMAP、ModelVerse 和通知投递
├── scripts/package.sh  # 交叉编译、打包和上传
├── go.mod
└── go.sum
```

开发时可在项目根目录运行 `go run ./cmd/signal-desk`。测试文件放在对应的包中。已有部署可用相同的 `-data` 目录启动新版，继续使用原 SQLite 数据和配置密钥。

## 配置邮件监控

1. 在「通知渠道」添加邮件、飞书群机器人或通用 Webhook。一个邮件渠道可添加最多 50 个目标邮箱，每行一个或用逗号分隔。相同地址只投递一次，每位收件人都有独立的邮件、投递状态和重试记录。使用邮件渠道时，在「发信服务器」配置共享 SMTP 服务。IMAP 和 SMTP 均支持 TLS 直连和 STARTTLS。邮箱账号可填写服务商发放的应用授权码。SMTP 用户名留空表示服务端允许免鉴权中继，有用户名时使用 AUTH PLAIN。
2. 在「收件邮箱」添加 IMAP 账号、文件夹和检查计划。可填写五字段 Cron，例如 `*/5 * * * *`，也可在前面加秒字段或使用 `CRON_TZ=Asia/Shanghai` 指定时区。Cron 留空时按轮询间隔检查。首次成功连接默认从当前最新邮件之后开始，可勾选「首次读取已有邮件」进行回溯。建议配置好规则后再启用收件邮箱。
3. 在「邮件规则」绑定收件邮箱，填写主题正则和正文提取规则。主题可填 `(?i)工单|alert`，正文可按以下方式逐行配置。

   ```text
   工单号*=工单号[：:]\s*([A-Z0-9-]+)
   客户=客户[：:]\s*([^\n]+)
   ```

   提取器取第一个捕获组，正则无捕获组时取整个匹配。字段名末尾的 `*` 表示必填。缺失必填字段时会保存已提取的内容和错误详情。正文优先用纯文本，只有 HTML 时转换为文本。原邮件大小上限为 5 MiB。工具会跳过带有自身发信标记的通知，避免收发使用同一邮箱时循环触发。
4. 点「预览样例」检查主题和正文能否匹配。保存规则后，到「告警策略」选取该规则、通知模板和客户接收渠道。每封邮件可命中多条规则，同一规则可配置多条策略。

邮件变量包括 `{{.Subject}}`、`{{.From}}`、`{{.ReceivedAt}}`、`{{.Rule}}` 和 `{{.Body}}`。提取字段可用 `{{index .Fields "工单号"}}`。提取字段命名为 `model` 或 `模型` 时可用 `{{.Model}}`，命名为 `offline_at` 或 `下线时间` 时可用 `{{.OfflineAt}}`。

将下线表格提取到 `models` 字段，即可在样例预览和全链路事件中看到 `Models` 和 `OfflineAt`。每条模型记录有 `ModelName`、`OfflineTime` 和 `ReplacementModel`，均可为空。可按行用制表符或 `|` 分隔三列，以明确空列。连成一行的记录按日期拆分。整体下线时间优先使用单独提取的 `offline_at`，否则取所有非空记录中相同的时间，时间不一致时留空。邮件模板可用 `{{range .Models}}{{.ModelName}}{{end}}` 遍历这些记录。通用模板可用 `{{if .MailModels}}` 区分邮件下线表格和模型监控的 ID 列表。

## 配置模型监控

在「模型监控 → 定时与通知」设置模型列表 URL、可选 Bearer Token 和 Cron 表达式。默认接口为 [ModelVerse 模型列表](https://api.modelverse.cn/v1/models)。

| 表达式 | 执行时间 |
| --- | --- |
| `*/5 * * * *` | 每 5 分钟 |
| `0 9 * * *` | 每天 09:00 |
| `0 */15 * * * *` | 每 15 分钟，在第 0 秒执行 |
| `CRON_TZ=Asia/Shanghai 0 9 * * 1-5` | 北京时间周一到周五 09:00 |

默认使用服务端本地时区。五字段依次为分、时、日、月、星期。六字段在最前面加秒。已有轮询任务继续按保存的间隔运行，填写并保存 Cron 后切换。

- 「模型列表 → 查询最新模型」会立即排队请求接口，定时监控停用时也可使用。第一次成功请求建立基线，之后按模型 ID 识别上下线。价格或提供方等模型属性变化也会记录，列表顺序变化视为无变化。
- 在「告警策略」选择「模型监控上线」或「模型监控下线」，分别为客户配置模板和接收渠道。每次检查按变更方向汇总模型。可用 `{{.Count}}`、`{{.Time}}`、`{{.Source}}` 和 `{{range .Models}}{{.}}{{end}}`。
- 「请求日志」记录每次请求的触发方式、时间、HTTP 状态、耗时、模型数和更新结果。上下线详情可展开。接口失败时保留最近一次成功快照。有效的空数组代表全部模型下线。

## 通知模板与告警策略

「通知模板」预置模型已完成上线、模型已完成下线和模型提前下线三类模板，可编辑或新增。模板正文可选纯文本或 HTML，可用 `{{.Customer}}` 和 `{{.Channel}}` 填入客户和渠道名称。选择 HTML 后可直接编辑标签或点击「插入表格示例」。邮件保留 HTML 和表格，并包含纯文本备用正文。飞书将正文文本和普通 HTML 表格转换为卡片，排版以飞书显示为准。通用 Webhook 的 `body` 保留 HTML，另附 `"body_format":"html"`。原模板按纯文本处理。

在「通知渠道」填写客户名称并添加收件地址，同一客户可以有多个渠道。然后为每种「触发事件、模板、客户接收渠道」组合创建一条告警策略。例如：

| 触发事件 | 模板 | 客户接收渠道 |
| --- | --- | --- |
| 邮件规则命中「供应商模型变更」 | 模型提前下线 | A 客户的邮箱 |
| 邮件规则命中「供应商模型变更」 | 模型已完成下线 | B 客户的飞书 |
| 模型监控上线 | 模型已完成上线 | A 客户的邮箱 |
| 模型监控下线 | 模型已完成下线 | A 客户的邮箱 |

策略可选填模型 ID 正则，只通知匹配的模型。邮件策略从提取结果读取模型 ID。提前下线通知可使用邮件规则提取的计划下线时间。模型列表接口用于比较实际的上线和下线。旧版规则和模型监控里的通知配置会在升级时导入模板与告警策略。

「接口日志」可按后台访问或外部请求筛选，查看时间、操作、状态、耗时、错误及关联编号。模型 HTTP 查询、飞书和 Webhook 投递逐次记录，IMAP 按邮箱检查记录，SMTP 按投递尝试记录。同一日志也输出到服务端。外部日志只记录目标主机，后台访问只记录路由，日志中省略 URL 参数、认证信息和请求正文。

## 通知测试和全链路排查

在「通知测试」选择已启用的模板和接收渠道，可填入示例模型和邮件提取字段。先预览目标、标题和正文，再点「发送测试」。邮件渠道会向该渠道配置的每个地址投递，飞书和 Webhook 也走正式投递流程。手动测试的投递失败后可在「全链路日志 → 通知测试」按条重试。若只想测试自己的邮箱，选择 SMTP 临时地址即可。

在「发信服务器」保存 SMTP 配置后，点「检测发件地址」验证连接、TLS、登录和 `MAIL FROM`。如果要验证服务器能否接收邮件，填入自己的测试邮箱，再点「发送测试邮件」。结果会显示失败阶段、SMTP 状态码和脱敏后的服务端回复。服务器只允许授权账号代发时，请使用登录邮箱作为发件地址，或先在邮件服务端授权代发。

在「收件邮箱」点「立即检查」，然后打开「全链路日志 → 收件检查」查看对应记录。每条链路展示连接、邮件主题是否命中、正文提取结果、策略与模板、实际入队及投递。展开事件可查看提取到的字段值，展开投递可查看各次尝试和协议阶段。修正配置后可对失败或等待重试的通知点「立即重试」。模型检查和 SMTP 测试也可在全链路日志中查看。

## 通知与运行记录

飞书渠道使用群自定义机器人的 Webhook，可选签名密钥。每次推送同时校验 HTTP 状态和飞书业务状态。 [飞书机器人官方文档](https://open.feishu.cn/document/client-docs/bot-v3/add-custom-bot?lang=zh-CN)

通用 Webhook 以 JSON 发送 HTTP POST，收到 2xx 视为成功。支持可选 Bearer Token，配置 Token 时须使用 HTTPS。

```json
{"delivery_id":42,"event_id":21,"event_type":"model_up","title":"模型上线 · 1 个","body":"以下模型已上线：\n- provider/example-model"}
```

`Idempotency-Key` 和 `delivery_id` 在同一投递的重试中保持稳定。事件记录、任务游标与待发送通知在同一个 SQLite 事务内保存。渠道失败单独退避重试，总计最多 5 次。SMTP 5xx 拒绝会直接标记失败，之后可在「运行记录 → 通知投递」手动重试。重试使用最新的渠道密钥和 SMTP 配置。接收地址变更后，旧通知仍绑定原地址。外部服务已接收、但本地来不及写入成功状态时，后续重试可能重复投递。

默认数据目录包含 `signal-desk.db` 与 `config.key`。后台保存的服务器和渠道配置经 AES-GCM 加密。备份时先停止服务，并将整个数据目录一起保存。后台记录页展示各类别最近 100 条。

日志页可以清除所选类别的历史日志。接口日志、模型请求日志、运行与链路日志分别清理。运行与链路清理会删除已发送、已失败的投递，保留执行中的任务、待发送和发送中的通知及其关联记录。全链路日志逐条显示邮件投递的目标地址。收件进度、模型快照和配置仍可继续使用。清除接口日志后，新的后台访问和外部请求会继续记录。
